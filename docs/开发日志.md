### 一、架构定位问题

#### ❌ P0 — 系统不是 Agent，是流水线

`agent/workflow.py` 是一条硬编码的 9 步线性流水线。LLM 不驱动工具调用、不做决策、不管反馈。模型只是一个"文笔助手"，在 Step 2 被叫一次，输出一段文案，然后流程头也不回地走下去。

- 没有 Thought → Action → Observation → 再 Thought 的循环
- 如果教室查询返回 0 间，流程不回头、不让模型重新决策
- 本质是"带 LLM 文案的规则引擎 + 数据处理流水线"，不是 Agent

#### ❌ P0 — 两套方案生成路径字段不兼容

| | `agent/workflow.py`（命令行） | `web/app.py`（Web 端） |
|---|---|---|
| LLM 调用 | `llm_client.call_llm_for_ideation` | `plan_generator.call_llm_for_plan` |
| 方案字段 | `title` / `timeline` / `resources` / `promotion` | `activity_purpose` / `activity_content` / `activity_materials` |
| `agent/formatter.py` 期望 | ❌ 不匹配 → 活动目的/内容/物资永远为空 | ✅ 匹配 |

**影响**：命令行模式生成的 HTML 策划书缺少活动目的、活动内容和物资清单。

- 新增 `agent/agent_loop.py`（~500 行）：Agent Loop + 8 个工具定义 + AgentState + 降级流水线
- 更新 `main.py`：入口改为 `from agent.agent_loop import run_agent`
- 保留 `agent/workflow.py`：后续可删除（已无引用）

**8 个工具**：
1. `parse_user_input` — 意图解析
2. `analyze_and_expand_topic` — 主题分析扩展
3. `generate_activity_plan` — 方案生成

### P1：Agent Loop 缓存优先（Cache-First）重构

参考 Reasonix 的四支柱架构，将 Agent Loop 改造为 **"不可变前缀 + 追加日志 + 易变暂存"** 三层模型：

**架构变化**：

```
不可变前缀（Immutable Prefix）     ← 永远不修改，前缀缓存 100% 命中
  ├─ System Prompt（含记忆块）
  └─ 第一条用户输入

追加日志（Append-Only Log）        ← 只追加不删除，保护后续缓存
  ├─ LLM 回复 + 工具调用
  └─ 工具返回结果

易变暂存（Volatile Scratch）       ← 系统干预统一收集，作为单条消息追加
  └─ Todo Nag / 预算警告
```

**具体修改**：

#### 1. `agent/memory/trim.py` — 全面重构

| 函数 | 变更 | 说明 |
|------|------|------|
| `trim_to_budget()` | **改为 no-op** | 旧版从头部删除消息会破坏全部前缀缓存，现在不做任何裁剪 |
| `soft_trim_check()` | **新增** | 分层检查：软预算线（8000 tokens）仅警告不删除；硬预算线（64000 tokens）触发一次性压缩 |
| `hard_trim_to_budget()` | **新增** | 紧急压缩：保留 system 消息 + 最近 ~4000 tokens，中间部分用摘要替代。仅在接近模型上限时触发（正常 15 轮 Agent 循环不会触及 DeepSeek 128K 上限） |
| `DEFAULT_TOKEN_BUDGET` | 保留 | 8000 tokens（软预算线，触发效率提醒） |
| `HARD_TOKEN_BUDGET` | **新增** | 64000 tokens（硬预算线，触发一次性压缩） |

**为什么 8000 → 64000 有这么大差距**：DeepSeek V4 上下文窗口为 128K tokens。15 轮 Agent 循环（每轮：user msg ~50 + assistant ~200 + tool result ~200）≈ 6750 tokens，远低于 64K 硬预算。正常情况完全不需要裁剪，前缀缓存持续命中。

#### 2. `agent/agent_loop.py` — Scratch 机制重构

**问题 → 修复**：

| 问题 | 旧行为 | 新行为 |
|------|--------|--------|
| Todo Nag 注入 | `messages.append(nag)` 在循环中间，位置随条件漂移 | `_collect_scratch_notes()` 收集所有 nag，`_flush_scratch()` 统一追加到末尾 |
| Token 预算裁剪 | 每轮 `trim_to_budget()` 从头部删消息 | 仅在 `should_hard_trim=True` 时做一次性压缩（正常不触发） |
| 无工具调用 Nag | 立即 `messages.append(nag)` | 仍然立即追加（需要 LLM 纠正），但追加位置固定（末尾） |
| 多 nag 导致碎片化 | 每个 nag 单独一条 user 消息 | 所有 scratch 合并为一条 user 消息追加 |

**新增函数**：
- `_collect_scratch_notes(state, messages)` → `list[tuple]`：收集本轮所有系统干预
- `_flush_scratch(messages, scratch_notes, trace)` → `list`：合并 scratch 为单条消息追加

**核心原则**：
1. ✅ 永远不删除消息（保护前缀缓存）
2. ✅ 系统干预统一收集到 scratch，作为单条消息追加
3. ✅ 仅在线性预算临界时做一次性压缩（而非每轮裁剪）
4. ✅ 工具定义作为 API 参数传递，不在消息体内（DeepSeek 按完整 payload 做前缀匹配）

## 2026-06-02（续）— 代理默认关闭 + 空白地址 修复

### 变更原因

- 原有代理默认 `http://127.0.0.1:7897` 为个人开发环境地址，对其他用户不可达
- 代理默认开启会导致无代理环境的 API 调用全部失败（非必要障碍）
- 参考 Reasonix 的 "零配置启动" 理念，代理应该是 opt-in 而非 opt-out

### 修改文件

| 文件 | 位置 | 旧值 | 新值 |
|------|------|------|------|
| `agent/proxy.py:5` | `_default_proxy` | `'http://127.0.0.1:7897'` | `''`（空字符串） |
| `web/app.py:56` | session 初始状态 | `proxy_enabled: True` | `proxy_enabled: False` |
| `web/app.py:57` | session 初始状态 | `proxy_address: 'http://127.0.0.1:7897'` | `proxy_address: ''` |
| `web/app.py:64` | `_apply_proxy` 默认值 | `state.get("proxy_enabled", True)` | `state.get("proxy_enabled", False)` |
| `web/app.py:158-159` | GET `/api/proxy` 有 session | `True` / `'http://127.0.0.1:7897'` | `False` / `''` |
| `web/app.py:161-164` | GET `/api/proxy` 无 session | `True` / `'http://127.0.0.1:7897'` | `False` / `''` |
| `web/templates/index.html:308-309` | JS 变量初始值 | `proxyEnabled = true` / `proxyAddress = "http://..."` | `proxyEnabled = false` / `proxyAddress = ""` |
| `web/templates/index.html:317-318` | JS 读取 localStorage | `cfg.enabled !== false` / `cfg.address \|\| "http://..."` | `cfg.enabled !== undefined ? cfg.enabled : false` / `cfg.address \|\| ""` |

### 用户影响

- ✅ 全新安装不配置代理即可直接使用 DeepSeek API（无需在 UI 中手动关闭代理）
- ✅ 之前保存过代理设置的用户不受影响（localStorage 优先）
- ✅ 页面右上角代理开关状态指示灯：默认灰色（关闭）而非绿色（开启）

### 🔴 P0 级缺陷（影响可靠性，必须修）

#### P0-1：Skill 系统完全悬空 — 6 个 SKILL.md 是死代码

`agent/skill_loader.py` 能扫描和匹配 Skill，但 `agent_loop.py` 的 system prompt **从未注入匹配到的 Skill**。只有 `plan_generator.py` 做了 `SKILL_TO_CATEGORY` 的弱映射（只拿 category 标签，不拿 SOP 内容）。

**违背的原则**（agent.md 第四期）：Skill 的价值 = 降低随机性，沉淀方法论。Agent 策划"竞赛"和"讲座"用同一套流程，不会根据 Skill SOP 调整策略。

**修复方向**：Agent Loop 启动时调用 `match_skill()` → 注入 SOP 表到 system prompt 的 `## 当前技能指引` 段落；host_guides / materials 模板喂给 plan_generator。

---

#### P0-2：Sub-Agent 不是 Agent — 无 LLM 驱动、无上下文隔离

`agent/tools/subagent.py` 的 `classroom_scout` 和 `budget_analyst` 本质是 Python 函数——直接调 `query_rooms()` / `rank_rooms()` / `estimate_budget()`，没有任何 LLM 参与。

**违背的原则**（agent.md 第五期）：子代理的价值是"多一个干净上下文"，有自己的 `messages[]`，跑完只回传摘要。真正的子代理如果 `find_classrooms` 返回 0 间，会自己决定扩大搜索范围。

**修复方向**：重构为 `run_subagent(prompt, agent_type) → summary` 模式，子代理有自己的 messages + 白名单工具 + max_turns。

---

#### P0-3：无死循环检测（Circuit Breaker）

`MAX_TURNS=15` 存在，但**没有检测"同一工具同样参数连续调用"**。

**违背的原则**（agent.md 第三期）：模型在不确定时会反复绕圈（同一工具同样参数再调一次），必须设断路保护。

**修复方向**：连续 3 轮同一工具+同一参数 → 注入 `[Circuit Breaker] 你已重复调用此工具 3 次，请换一种方式或跳过此步。`

---

#### P0-4：Finalize 前置校验缺失 — 模型说 done ≠ 真的 done

TodoWrite 约束全靠 system prompt 软约束，LLM 可在 todo 列表有 `pending` 项时直接调 `finalize`。

**违背的原则**（agent.md 第四期坑②）：模型会"伪造更新"——只说"我更新了"但不调工具。Harness 必须代码级校验。

**修复方向**：在 `dispatch_tool("finalize")` 中拦截——如果还有 pending/in_progress 的 todo，返回 error 而非允许结束。

---

### 🟡 P1 级缺陷（影响稳定性，应该修）

#### P1-5：System Prompt 无「环境信息」注入

System prompt 纯静态，没有注入当前可用的教室数量/分布概况、建筑列表、学期阶段等环境信息。模型在"盲选"教室。

**违背的原则**（harness.md L2 层）：上下文架构应按需加载环境信息，而非让模型猜测。

---

#### P1-6：工具返回结果无 Token 截断

所有工具返回 `json.dumps(result)` 全量输出。如果 Tavily 返回 10 条长结果，单次 observation 可能占几千 token。

**违背的原则**（agent.md 第三期）：工具返回结果必须纳入预算，observation 也要截断。

---

#### P1-7：无 Post-Tool-Call 验证层

工具执行完就完了。`generate_activity_plan` 返回缺字段 JSON、`find_classrooms` 返回 0 间——都没有自动检测和修正建议。

**违背的原则**（harness.md 反馈闭环）：Agent writes → Harness 自动验证 → 若 fail 把 error 塞回 observation → Agent 修订。

---

#### P1-8：工具数量已到决策疲劳边界

12 个工具中，`parse_user_input` + `analyze_and_expand_topic` + `generate_activity_plan` 可合并为 `plan_activity` 复合工具；`find_classrooms` + `score_classrooms` 可合并为 `find_best_classroom`；`dispatch_subagent` 目前无实际价值。

**违背的原则**（harness.md 原则 2）：工具不是越多越好，每个 step 的 tool-choice 选错概率随工具数上升。

## 2026-06-03 — P0-2 修复：Sub-Agent 重构为真正的 LLM 驱动 Agent

### 为什么要修？

旧版 `agent/tools/subagent.py` 的 `classroom_scout` 和 `budget_analyst` 本质上是两个 Python 函数：

```python
# 旧代码：直接调函数，没有 LLM 参与
def _scout_classrooms(prompt, state):
    rooms = query_rooms(...)       # 查一次
    if not rooms:
        return "暂无可匹配教室"     # ← 直接放弃！不会自己想办法
    sorted_rooms = rank_rooms(...)
    return json.dumps({...})
```

这违背了 Agent 教学第五期的核心定义：

> 子代理的价值不是"多一个模型实例"，而是"多一个干净上下文"。真正的子代理如果 `find_classrooms` 返回 0 间，会自己决定扩大搜索范围。

**具体症状**：
- 查教室返回 0 间 → 子代理直接返回空结果，不会尝试换建筑/降容量/去设备筛选
- 无法做多轮探索（"先查 E 座 → 不够再查 D 座 → 综合评分"）
- 预算分析只是调函数返回数字，没有分析和优化建议

### 怎么修的？

**架构：从「函数调度器」→「微型 Agent Loop」**

```
旧架构：
  dispatch_subagent → _scout_classrooms() → query_rooms() → return JSON
                    → _analyze_budget()   → estimate_budget() → return JSON

新架构：
  dispatch_subagent → run_subagent()
    ├─ ① 创建隔离 messages[]（system_prompt + 工单）
    ├─ ② 提取白名单工具（classroom_scout 只有 3 个工具）
    ├─ ③ 运行微型 Agent Loop（最多 N 轮）
    │    ┌─ LLM 调用（只有白名单工具可选）
    │    ├─ 执行工具调用
    │    ├─ 追加结果到 sub_messages
    │    └─ 无工具调用 → 任务完成
    └─ ④ 返回最终文本摘要（sub_messages 被丢弃）
```

**三个"★"就是第五期的灵魂**：

| ★ | 含义 | 实现 |
|---|------|------|
| `sub_messages = [干净起始]` | **上下文隔离** — 不继承父 Agent 的任何 messages | `run_subagent()` 内局部变量，函数返回后自动回收 |
| `whitelist_tools`（白名单） | **权限边界** — 子代理拿不到父 Agent 的全部能力 | 从 `TOOL_DEFINITIONS` 按 `spec.tool_names` 过滤 |
| `return summary` | **只带回摘要** — 子代理全程产生的 messages 不写回父 Agent | `final_summary` 字符串，其余数据跟随函数栈帧销毁 |

**子代理身份（花名册）**：

| 子代理 | 白名单工具 | 最大轮次 | 职责 |
|--------|-----------|:--:|------|
| `classroom_scout` | find_classrooms, score_classrooms, get_navigation | 6 | 查询教室→空则扩大搜索→评分→导航→返回摘要 |
| `budget_analyst` | calculate_budget | 4 | 计算预算→分析构成→指出主要支出→优化建议 |

**防止无限递归**：子代理白名单中不包含 `dispatch_subagent`，确保子代理不能再派子代理。

**降级保护**：如果 LLM API Key 未配置，自动回退到确定性函数兜底（保留旧行为，保证基本可用）。

### 结果验证

测试场景：为 30 人讲座找教室，数据库中暂无可匹配教室。

**旧子代理行为**：
```
find_classrooms(30, E教学楼) → 0 间 → "暂无可匹配教室" → 放弃
```

**新子代理行为**（LLM 自主决策，5 次尝试）：
```
Turn 1: find_classrooms(30, E教学楼, 投影仪) → 0 间
Turn 2: find_classrooms(30, E教学楼, 无设备) → 0 间     ← 自动去掉设备筛选
Turn 3: find_classrooms(20, E教学楼, 投影仪) → 0 间     ← 自动降低容量
Turn 4: find_classrooms(20, E教学楼, 无设备) → 0 间     ← 同时降容量+去设备
Turn 5: find_classrooms(10, E教学楼, 无设备) → 0 间     ← 继续降低
→ 总结："系统中目前没有任何可用教室数据"                    ← 用自然语言报告发现
```

新子代理在遇到空结果时**自主尝试了 4 种不同的搜索策略**，而不是直接放弃。
