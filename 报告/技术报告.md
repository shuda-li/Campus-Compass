# Campus Compass 校园活动智能策划 Agent · 技术报告

---

## 一、项目介绍

### 1.1 项目背景

高校学生组织（学生会、社团等）每年需要策划大量校园活动，从确定主题、设计环节、预估物资到选择场地，传统方式依赖人工经验和纸笔记录，效率低下且容易遗漏关键信息。大语言模型（LLM）的快速发展为自动化活动策划提供了可能，但纯对话式 LLM 无法获取真实的教室数据、无法计算预算，也缺乏领域知识来指导特定类型活动的策划流程。

Campus Compass 正是针对这一痛点设计的智能 Agent 系统。它将 LLM 的推理能力与工具调用、技能库、记忆系统相结合，通过多轮对话自动生成结构化活动方案，并在方案生成后支持精确的迭代修改。

### 1.2 项目目标

本项目旨在构建一个面向校园活动策划场景的智能 Agent，核心目标包括：

1. **自动化方案生成**：用户输入活动主题后，Agent 自主调用工具完成意图解析、教室查询、预算计算、方案生成的全流程，输出包含活动目的、环节设计、物资清单、场地推荐、预算估算的完整方案。
2. **精确的修改定位**：方案生成后，用户的修改需求（如"把活动时间改为周三"）能被精准锚定到方案 JSON 的对应字段，而非重新生成整个方案。
3. **领域知识复用**：通过 Skills 系统管理 6 种活动类型的 SOP 模板，关键词匹配命中后自动注入到 LLM prompt 中，确保方案专业性和一致性。
4. **优雅的用户体验**：提供星穹铁道主题的 Web 界面，支持流式输出、一键导出 Word 文档。

### 1.3 功能需求

| 编号 | 功能 | 说明 |
|------|------|------|
| F1 | 意图解析 | 从自然语言中提取活动类型、人数、建筑偏好等 |
| F2 | 主题扩展 | 简略主题（如"篮球赛"）自动扩展为完整描述 |
| F3 | 方案生成 | LLM 生成包含 5 个环节、物资清单的结构化 JSON |
| F4 | 教室推荐 | 基于容量和拓扑距离双维度评分推荐最优教室 |
| F5 | 预算计算 | 根据活动类型和人数估算详细预算 |
| F6 | 修改意图检测 | 5 种修改类型 × 3 层漏斗检测，支持关键词锚定 |
| F7 | Word 导出 | 一键导出完整方案为 .docx 文件 |
| F8 | 记忆系统 | L1/L2/L3 三级记忆，持久化用户偏好 |

## 二、系统设计

### 2.1 系统架构

系统采用 **Agent / Skill / Harness 三层架构**：

```
┌─────────────────────────────────────────┐
│               Web UI (Flask)             │
│   SSE 流式  │  会话管理  │  Word 导出    │
├─────────────────────────────────────────┤
│            Agent 层 (决策引擎)            │
│  ReAct Loop │ Circuit Breaker │ SubAgent │
│  LLM Client │ Tool Registry   │ Formatter│
├─────────────────────────────────────────┤
│         Engine 层 (业务引擎)             │
│  Plan Generator │ Plan Anchor           │
│  Intent Detector│ Room Scorer/Selector   │
│  Topic Analyzer │ Completeness Checker   │
├─────────────────────────────────────────┤
│       Harness 层 (安全护栏)              │
│  Token Budget │ Trace Logger │ Memory    │
├─────────────────────────────────────────┤
│         基础设施层                        │
│  SQLite │ JSON Map │ Skills MD × 6      │
│  Tavily Search │ DeepSeek API           │
└─────────────────────────────────────────┘
```

### 2.2 核心模块划分

| 模块 | 职责 | 关键文件 |
|------|------|----------|
| Agent Loop | ReAct 循环，缓存优先架构 | `agent/agent_loop.py` |
| Tool Registry | 11 个工具的白名单注册与调度 | `agent/tools/registry.py` |
| Plan Anchor | 方案倒排索引构建 + 三层匹配 | `engine/plan_anchor.py` |
| Plan Patcher | 简单修改直接 patch JSON | `engine/plan_patcher.py` |
| Intent Detector | 5 类型 × 3 层漏斗修改意图检测 | `engine/intent_detector.py` |
| Skill Loader | 关键词匹配 + LLM 语义分类兜底 | `agent/skill_loader.py` |
| Memory | L1 会话 + L2 SQLite + L3 JSON | `agent/memory/` |
| MCP Search | Tavily 搜索 + DeepSeek 降级 | `agent/mcp/tavily_search.py` |
| Sub-Agent | 子代理隔离上下文执行专项任务 | `agent/tools/subagent.py` |

### 2.3 设计思路

**ReAct 循环**是系统的核心控制流。Agent 在每轮对话中经历 Thought → Action → Observation 三个阶段，自行决定调用哪些工具、以何种顺序调用。为防止死循环，系统内置了 Circuit Breaker 检测连续重复工具调用。对于复杂任务，Agent 通过 TodoWrite 机制先规划步骤再逐步执行，确保流程可控。

**Plan-Aware 关键词锚定**是本项目的原创设计。方案生成后，系统从方案 JSON 提取所有文本字段构建倒排索引。当用户输入修改需求时，通过精确匹配 → 子串匹配 → 模糊匹配三层策略反向定位目标字段。对于简单的确定性修改（时间、主办方等），系统直接 patch JSON，完全跳过 LLM，实现零延迟修改。

**缓存优先架构**参考了 DeepSeek 的前缀缓存机制。将 System Prompt 和首条用户输入固定为不可变前缀（永不修改，保证前缀缓存 100% 命中），LLM 回复和工具返回仅追加不删除，系统干预统一收集为单条暂存消息追加到末尾。

**Sub-Agent 隔离**将教室查询和预算分析两个子任务封装为独立子代理，拥有独立的 messages[] 上下文和工具白名单。子代理可以自主尝试不同搜索策略（如教室查询为空时自动扩大范围），完成后退回摘要，对话上下文不污染父 Agent。

## 三、系统开发

### 3.1 核心技术实现

**ReAct Agent Loop**：基于 agent/agent_loop.py 实现，核心流程为：(1) 构建 immutable prefix（system prompt + 工具定义 + 首条用户输入）；(2) 调用 LLM 获取回复；(3) 若 LLM 返回 tool_calls，则 dispatch 到对应工具并追加 observation；(4) 若 LLM 返回纯文本，则追加到日志；(5) 循环至 LLM 调用 finalize 或达到轮次上限。每轮检查 Token 预算，接近临界时触发软/硬压缩。

**Plan-Aware 锚定系统**：Plan 生成后由 plan_anchor.py 的 build_plan_index() 从 organizer、activity_content[].phase、activity_materials[].name 等字段提取关键词构建倒排索引，同时注入字段中文别名（如"主办单位"→organizer）。anchor_feedback() 以三层匹配策略（exact→substring→fuzzy）定位修改目标，format_anchor_hint() 将锚定结果格式化为 LLM prompt 提示块。

**混合修改模式**：plan_patcher.py 将修改分为两类——时间/主办方/承办方/人数等简单字段修改直接提取新值 patch JSON；增删环节/改写内容/调整物资等复杂修改走 LLM，但以原始 plan JSON 为 base 进行修改而非重新生成。实测简单修改可实现零 Token 消耗、零延迟响应。

**三级记忆系统**：L1 为会话字典（当前对话上下文），L2 为 SQLite 持久化（跨会话历史记录），L3 为 .memory/ JSON 文件（长期用户偏好如常用建筑、惯用人数）。记忆加载块在每次 LLM 调用前注入 prompt，实现个性化体验。

### 3.2 未完成的功能与遇到的问题

在开发过程中，信息补全追问（completeness_checker）的追问质量不够稳定，有时会重复询问已提供的信息。此外，Word 导出功能依赖 python-docx 库，在保持 Star Rail 主题配色的前提下，复杂表格布局的兼容性偶有问题。

### 3.3 关键技术问题与解决

开发初期遇到的核心问题是修改定位不准确——用户说"改一下时间"，Agent 无法确定要修改哪个字段。通过构建 Plan 倒排索引 + 字段别名映射解决。另一个问题是纯关键词匹配无法覆盖所有表达方式（如"蔡徐坤演唱会"无关键词命中），通过新增"演唱会"等关键词 + _detect_topic_switch 增强检测（规则 D：全技能零命中 + 不像修改命令 → 判定为换题）来兜底。

## 五、总结与展望

### 5.1 项目总结

Campus Compass 成功构建了一个完整的 LLM 驱动的校园活动策划 Agent，涵盖了从意图理解到方案生成、从修改迭代到文档导出的全流程。项目实践了 ReAct Agent 架构、Tool-Use 模式、Sub-Agent 隔离、多层记忆系统、MCP 搜索工具等前沿 AI Agent 技术，并在 Plan-Aware 关键词锚定和混合修改模式方面做出了创新性设计。

### 5.2 学习收获

通过本项目，深入理解了 Agent 的核心设计模式：(1) ReAct 循环如何通过工具调用扩展 LLM 的能力边界；(2) 缓存优先架构如何利用 LLM 前缀缓存降低 API 成本；(3) Skills 和 Memory 如何为 LLM 注入领域知识和个性化上下文；(4) 倒排索引和渐进匹配在 NLU 中的实用价值。同时积累了 Flask SSE 流式输出、GitHub 项目管理等工程实践经验。

### 5.3 未来展望

未来可在以下方向继续改进：增加更多活动类型技能模板；引入 RAG 检索增强生成，从真实校园活动数据库中检索案例；增加 Human-in-the-loop 审核环节；支持多用户协作策划；实现 Docker 一键部署。

### 附录 A：Agent System Prompt（agent/agent_loop.py）

```
你是 Campus Compass 校园活动策划 Agent。你通过调用工具来完成活动策划任务。

## 任务规划规则
重要：对于任何复杂任务，你必须先调用 todowrite 列出计划步骤，再逐个执行：
- 收到任务 → 先调 todowrite 列出所有步骤 (pending)
- 开始某步 → 把该步翻成 in_progress
- 完成某步 → 翻成 completed
- 同一时间只有一个 in_progress
- 所有步骤 completed 后才能调 finalize

## 核心工具流程
1. parse_user_input — 解析用户意图
2. analyze_and_expand_topic — 分析/扩展主题
3. generate_activity_plan — 生成方案
4. find_classrooms — 查询教室（空则扩大范围）
5. score_classrooms — 评分排序（如有教室）
6. calculate_budget — 计算预算
7. finalize — 生成最终HTML

**重要：设置活动时间前必须先调 get_current_time 获取当前时间，活动时间不得早于当前时间。**

## 行为规则
- 不要猜测结果，调用工具获取真实数据
- 工具返回空或出错时，不要卡住，继续下一步
- 工具调用之间的文字输出简短即可
- 用户有长期记忆时，参考记忆中的偏好
- 如果用户在活动中表现出偏好，调用 save_user_preference 保存
- 对于不熟悉的活动主题，可以使用 search_web 搜索背景知识和案例来丰富方案内容
```

核心原则:
