AI 圈名词爆炸（LLM → Prompt → RAG → MCP → **Agent / Skill / Harness**），不是谁在故意造词，而是**每一次落地卡住，就逼出一个新层**。这三个词解决的是同一个问题：**怎么让 AI 从"会说话"变成"能把事稳定做完"**。

它给的核心定位：

| 概念          | 一句话（视频口径）                         | 相当于            |
| ----------- | --------------------------------- | -------------- |
| **Agent**   | 干活的"主体"——理解目标、拆步骤、调工具、闭环推进        | 项目经理 / 大脑      |
| **Skill**   | 把一类事沉淀成**可复用能力包**，降低随机性           | 员工的手艺 / SOP 手册 |
| **Harness** | Agent 的**运行底座**——管安全、管边界、管调度、管可观测 | 马具 / 工位 / 纪律委员 |

***

## 逐段还原：视频到底在论证什么

### 0′00″–0′40″｜为什么会有这么多词？

视频开头的论点（也是它最值钱的一句）：

> 这些名词不是凭空发明的，而是**每一层解决完一个问题之后，下一层瓶颈就浮出来了**：
>
> 1. **LLM**：文字接龙，能"想"但不能"做"
> 2. **Prompt Engineering**：让模型更听话（角色、示例、约束）→ 解决"听不听得懂指令"
> 3. **RAG**：弥补模型知识盲区 → 解决"知不知道"
> 4. **Tool Use / Function Calling**：终于能让模型碰外部世界 → 但跑起来就发现——**不受控、不稳定、不可观测**
> 5. 于是拆出 **Agent（主体）→ Skill（能力模块）→ Harness（运行底座）** 来分别治之

***

### 1′00″前后｜Agent：从"问答器"升级为"执行者"

视频把 Agent 从 Chatbot 划清界限：

- **Chatbot 终点** = 输出一段文本
- **Agent 模式**下模型的任务升级为：
  ```
  理解目标 → 规划步骤 → 选工具 → 执行 → 看反馈 → 再决策 → …
  ```
- 举例锚定：Claude Code / Codex 这类编码 Agent 的本质就是**把大模型从"问答器"变成了"执行者"**

**视频想你带走的判断**：Agent 的核心不是"更聪明的模型"，而是**带循环的调用链**（也就是我们第二期手搓的那个 `while + tool_use`）。

***

### 2′00″–3′00″｜Skill：可复用能力包（不是"更长的 prompt"）

视频讲 Skill 的出发点非常精准：

> Agent 虽然会推理，但**不意味着每次都能稳定地把同一类任务做好**。\
> Skill 的价值 = **降低随机性，沉淀方法论**。

它给出的 Skill 画像（结合通义系的定义）：

- Skill 不是一个函数，也不是一句 prompt
- 它是一个**文件夹/包**，里面通常有：
  - `SKILL.md`：触发条件 + 步骤 + 约束 + 输出格式
  - `scripts/`：真正执行的脚本/辅助代码
  - `references/`：参考资料、示例、模板
- 智能体在相关场景下**自动加载**对应 Skill，按 Skill 里规定的方法论干活
- Skill 解决的是：\*\*"可复用的专业能力怎么沉淀"\*\*这个问题

类比它最爱用的（或等价说法）：

> 给 AI 安装"技能包"——像孙悟空的 72 变，装上就有这门手艺。

***

### 3′30″–5′00″｜Harness：最陌生但最关键的那个（字面意思 = 马具）

这是视频的"压轴概念"。

**Harness = Harness（马具）**——套在马上、**控方向、控受力、控约束**的那套装置。放到 AI 里：

> Harness 不是模型，不是工具，不是某个 Skill；它是 **Agent 的运行底座 / 驾驭层 / 调度框架**，管四件大事：

| Harness 管的        | 具体指什么                                                         |
| ----------------- | ------------------------------------------------------------- |
| **安全控制**          | 权限边界、白名单、防危险操作（"纪律委员"）                                        |
| **流程管理 / 调度**     | 安排 Skill 的执行顺序、什么时候调哪个工具、怎么推进循环                               |
| **状态 & 上下文管理**    | 记忆、进度、上下文裁剪（防"失忆"和窗口爆炸）                                       |
| **可观测 / 反馈 / 容错** | 日志 trace、失败重试、评估打分——"没有 harness 它只是聊天机器人；有了它才变成可管理、可评估的工业级系统" |

视频用一句话收束（多方转载一致）：

> **Agent 决定"做什么"，Skill 决定"怎么做得更稳"，Harness 决定"在什么规则里做"。**

类比版本（视频或同源解读常用）：

- Agent = 士兵（整个人）
- Harness = 士兵的**大脑助理 + 指挥链路 + 纪律**（判断敌情、决定行动、保证不越界）
- Skill = 开枪 / 打电话 / 包扎（具体本事）

***

### 5′00″–6′16″｜收尾：三者怎么协作（完整工作流）

视频给的流程线大概是这样：

```
用户提目标
  → Harness 搭环境、准备上下文
    → Agent（大脑）分析，制定计划
      → Agent 调用 Skill（查资料/写代码/发邮件…）
        → Skill 执行，返回结果
      → Agent 根据结果决定下一步
    → Harness 监控全过程（安全/进度/日志）
  → 交付结果给用户
```

***

## 视频"讲了的"vs"没讲清但你要命的"（补坑环节）

### ⚠️ 坑①：视频把 Skill 说得像"文件夹包"，但没说清 Skill 与 Tool 的边界

**实操中最容易混的就是这两个：**

| <br /> | Tool / Function Call            | Skill                                         |
| ------ | ------------------------------- | --------------------------------------------- |
| 粒度     | 原子操作（run\_command / read\_file） | 组合流程（"发布文章"="调研格式→生成→排版→预览→确认→发布"）            |
| 有无智能   | 无（纯执行）                          | 有（内含方法论/步骤/判断点）                               |
| 怎么加载   | `tools=` 列表注册                   | 按场景匹配 → 注入 system/上下文 或 驱动 sub-agent 按 SOP 走  |
| 谁调度    | Agent 直接调                       | **Harness 发现场景 → 挂载 Skill → Agent 按 Skill 走** |

所以更准确的工程定义是：

> **Tool = 动词（能做什么）｜ Skill = SOP（怎么把多个动词组织成可靠流程）｜ Harness = 谁能在什么时候用什么动词、按什么 SOP、受什么约束**

***

### ⚠️ 坑②：视频的 Harness 定义偏"比喻"，没落到文件夹结构

如果你把手搓六期代码对应上去，Harness 在你项目里长这样：

```
agent/
  agent_loop.py        ← 循环调度（Harness 核心）
  state.py              ← AgentState: messages, todos, tokens…
  tools/
    registry.py         ← 工具注册表 + 白名单（Harness 的安全边界）
    dispatch.py         ← 工具路由（Harness 的调度）
  memory/
    trim.py             ← 上下文裁剪（Harness 的 budget 管理）
    persistence.py      ← 长期事实持久化
  harness/
    config.yaml         ← 权限/配额/路径锁（Harness 的"纪律手册"）
    observ.py           ← trace / 日志（Harness 的眼睛）
```

一句话：**Harness =** **`agent_loop`** **+** **`registry`** **+** **`trim`** **+** **`persistence`** **+** **`config`** **+** **`trace`**，不是神秘新东西。

***

### ⚠️ 坑③：视频没说清"Skill 谁来写、怎么触发、怎么保证不冲突"

落地时 Skill 的真正难点不是定义格式，而是三点：

1. **触发机制**：关键词匹配？语义匹配？Agent 自己判断？（建议：先让 Agent 有 `load_skill(name, reason)` 工具，别偷偷自动注入）
2. **Skill 冲突**：两个 Skill 对同一件事有不同 SOP → 需要优先级 / 作用域声明
3. **Skill 版本管理**：你改了 `publish-wechat-article/SKILL.md`，上次跑成功的流程为什么又挂了？

最小起步方案：

```yaml
# skills/publish-wechat-article/SKILL.yaml
name: publish-wechat-article
trigger:
  keywords: ["发布", "公众号", "微信文章"]
scope: workspace_only
requires_user_confirmation: true
max_turns: 20
```

***

### ⚠️ 坑④：视频的叙事暗示"三者是分层的"，但真实系统里边界会渗透

真实代码里你会发现：

- Agent 的 system prompt **属于 Harness**（因为它规定了规则和边界）
- `TodoWrite` 这个"工具"**又是 Skill 的微型版本**（外部化计划 = 结构化 SOP）
- 所以别死抠谁属于谁——更有用的是问：**这块状态归谁管？这块决策能不能观测和回滚？**

***
